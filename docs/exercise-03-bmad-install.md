## What survives reinstallation, and what may be overwritten

Taken from the headers of the installed files, not assumed.

### Overwritten on every install or update

| File | Header evidence |
| --- | --- |
| `_bmad/config.toml` | "Installer-managed. Regenerated on every install — treat as read-only." |
| `_bmad/config.user.toml` | "Installer-managed. Regenerated on every install — treat as read-only." |
| `.claude/skills/*/customize.toml` (27 of 29 skills) | "DO NOT EDIT -- overwritten on every update." |
| `_bmad/core/config.yaml`, `_bmad/bmm/config.yaml` | "Generated by BMAD installer" (version and date stamp). Treat as generated. |
| `_bmad/_config/*` (manifests, `files-manifest.csv` hashes) | Installer bookkeeping. Treat as generated. |
| Skill files (`SKILL.md`, steps, templates, references) | Installed from the BMAD package. Treat as replaceable on update. |

The two `config.toml` headers say answers given to the installer are remembered as defaults. A rerun therefore regenerates those files from the prior answers. It does not discard the answers.

### Survives reinstallation

| File | Header evidence |
| --- | --- |
| `_bmad/custom/config.toml` | Team overrides, committed. "Those files are never touched by the installer." |
| `_bmad/custom/config.user.toml` | Personal overrides, gitignored via `_bmad/custom/.gitignore` (`*.user.toml`). Never touched by the installer. |
| `_bmad/custom/<skill-name>.toml` and `<skill-name>.user.toml` | Per-skill override layers. `resolve_customization` / `config_utils.py` load them on top of the skill's `customize.toml`. The `custom/` directory is the documented override location. |
| `_bmad-output/` and `docs/` | Project output and knowledge folders set in the config. They are not installer-managed files. |

Merge order, from `_bmad/scripts/config_utils.py`:

- Config: `config.toml`, then `config.user.toml`, then `custom/config.toml`, then `custom/config.user.toml`. The last one wins.
- Skill customization: the skill's `customize.toml`, then `custom/<skill>.toml`, then `custom/<skill>.user.toml`.

Practical rule: never edit a file marked "DO NOT EDIT" or "Installer-managed". Put changes in `_bmad/custom/`. The `bmad-customize` skill authors those overrides.

## Skill description cost vs. runtime execution cost

**Description cost (always paid).** Claude Code lists every available skill's name and description in context, in every session. That is the 30–180 tokens per BMAD skill seen in `/skills`. It is a fixed overhead whether or not a skill is used. It grows with the number of installed skills (61 here) and with description length. Some BMAD descriptions are long, for example `bmad-deep-recon`.

**Execution cost (paid only on use).** The full `SKILL.md` loads only when a skill is invoked. A skill can then pull in step files, templates, references and scripts, and may run agents or tool calls. The cost depends on the workflow:

- `SKILL.md` sizes for BMAD skills range from about 0.7 KB (`bmad-build-auto`) to about 14 KB (`bmad-prd`), roughly 175 to 3,500 tokens by a rough 4-bytes-per-token estimate.
- The whole `.claude/skills/` tree is 214 files and about 2 MB. Almost none of it is in context until a skill runs.
- Multi-step workflows such as `bmad-build`, `bmad-prd` and `bmad-code-review` read more files as they go, and every step and tool result adds to the conversation.

Summary: the description cost is small and constant. The execution cost is much larger but only paid per invocation. Reducing the number of listed skills lowers the first. Choosing leaner workflows lowers the second.
